## 三、大量错误究竟是什么

所有 2280 份状态共 8267 次错误事件；其中开发调试 3892、开发验收 4090、公开在途及已完成状态 285。已评分的 1512 条轨迹共 8009 次事件。事件随轮次累计，不能按事件数解释为独立失败题数，也不能把相同初稿在十二组中的重复错误当成十二个独立问题。

### 1. 无效模型是主要来源，不是 CPU 集群频繁崩溃

`invalid_model` 共 4676 次，是控制器在模型不存在时记录的阶段失败；CPU 进程不一定被启动。两个开发子集分别有 23/60 个共同初稿无效。C0 每题三轮、每轮三个阶段，23×3×3=207，恰好解释各开发子集 C0 的全部 207 次错误。

全部 14678 条 CPU 执行事件均记录进程完成、exit_code=0、timedout=false。这说明没有这些事件所覆盖的进程崩溃/超时；**不等于每个 CPU 任务数学执行成功**，程序可以正常退出并返回 execution_error。状态中仍有一次 Invalid candidate vector 等应用层错误。

### 2. 重建模型反复产生同类索引错误

状态中 objective.linear 索引越界共 **2475 次**，全部发生于开发集审阅或补丁阶段。不能简单归因为零基/一基混淆：已核实的 MIS-16 样例在 25 行边表上使用 `sum_rows` 和 `row_index` 生成顶点目标，而变量只有 16 个，遇到第 17 行即报 `index 16 outside 0..15`。同时它把边表累加成一个约束，而不是为每条边分别建约束；即便仅消除越界，也不能认定语义正确。

样例初稿与一次后续重建返回了相同模型；用当前对应提交的 compile_math 在本地重放，两次均复现完全相同的越界错误。证据见 samples.json 中 case、初稿 `6997ab01…` 与补丁请求响应 `0382f206…`。这支持“错误数据绑定反复重建”的诊断，不支持自动平移或截断索引来修复。

### 3. 审阅预算内无法完成 JSON，且存在递归重复生成

10450 个响应中：9427 generated、989 incomplete_output、34 generation_error。989 个不完整输出包括审阅 973（均输出 1024 tokens）、补丁 15（3072 tokens）、初稿 1（8192 tokens）。审阅已返回响应共 5449，973/5449=17.86% 不完整。

原始审阅样例 `00371382…` 的 finish_reason 为 token_limit，包含大量重复嵌套的 and/not 逻辑。不能把所有截断都解释为“正常答案略长”，也不能据此直接增加 token 预算；需要限制递归结构、检查 schema 与生成退化，再在开发数据上验证。

34 次 generation_error 中 33 次是输入预算拒绝，1 次是 JSON 递归异常。约 2.3–2.6 万 token 的请求也可能超过轨迹剩余累计输入预算，不表示单次 32768 上限失效。

### 4. GPU 2 重启根因已定位

`gpu_failures/2-1793586708037708426.json` 指向 `logs/gpu-2-1793550271399359545.log`。该日志 traceback 为 `generation.JsonComplete → complete_object → json.JSONDecoder.raw_decode → RecursionError`，导致 GPU 子进程退出并由控制器重启。这次失败不是日志所证实的 CUDA OOM，也不是之前已经修复的设备放置断言。旧失败日志保留在包内，不能混淆时间线。

`complete_object` 当前只捕获 ValueError，未捕获 RecursionError；这解释为何停止条件解析能终止整个 worker。后续应将此类输出隔离为单请求失败，保持成本与错误记录，并以独立修复版本回归；本次诊断未改写冻结组件。

### 5. 主方法确实有补丁执行，但执行质量并不充分

开发验收 U2 的 60 条中 42 条至少有一次错误；350 次错误由 invalid_model 191、索引越界 114、不完整输出 41、输入预算拒绝 3、删除未知约束 1 构成。最终 39/60 模型可编译，39 条有合法补丁输出，共 114 次合法补丁。合法补丁可能为空或语义错误，不能把这些次数称为成功修复。

因此，“350 次错误意味着反馈从未运行”和“acceptance 通过意味着完全正常”都不成立。验收目前只检查执行发生过，不能替代输出有效性和错误分布检查。
