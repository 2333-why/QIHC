## 原因与修复范围

代码此前把多个原生求解器导入同一进程。OR-Tools 与独立 HiGHS 的符号冲突已有 [官方仓库 issue #5246](https://github.com/google/or-tools/issues/5246)；其报告覆盖 Linux、highspy 1.15.1 和 OR-Tools 9.14.6206。这与本次导入顺序和 undefined symbol 高度吻合。日志本身没有提供服务器动态库映射，不能编造具体误加载的库文件路径。

只修改冒烟导入顺序不足以解决正式 worker 后续混载。此次修复：

1. 每种后端使用独立的 `spawn` 进程池；一个进程终身固定一个后端，避免继承父进程已加载的 native 库。正式评分和 CPU 原题参考解都经过该隔离。
2. 总活跃任务仍不超过 24；默认 CP-SAT、SCIP、HiGHS 各 4 个槽，四种采样后端各 3 个槽。单个求解仍为 1 线程、同样 1/5/20 秒预算。各池复用进程，不按每个评分重新启动。
3. 添加运行时防混载检查、后端绑定检查、进程 PID 与已加载求解器模块验收。Linux 冒烟记录相关 `/proc/self/maps` 库路径，便于判断剩余系统路径污染。
4. 准备脚本先只读检查 `.e002-solvers-*` 的版本元数据，复用已下载的完整暂存目录；通过隔离验收后才原子移动到正式依赖目录。不升级 Torch/Transformers，不重新下载 LLM 权重。
5. 增加 Linux/Python 3.11 CI，分别测试 OR-Tools 9.14.6206、9.15.6755 与固定 HiGHS/SCIP 版本。混载诊断在一次性子进程内进行，正式正确性与续跑必须在隔离模式通过。

E001 的运行继续固定原 `b1e3a78` 工作树；不在 E001 工作树切换到这次修复。新 E002 指纹不同，不能与旧提交已经产生的评分混跑。此次用户的失败发生在环境准备阶段，没有证据表明需要重新生成模型。
